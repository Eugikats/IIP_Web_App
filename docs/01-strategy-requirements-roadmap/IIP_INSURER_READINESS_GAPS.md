# IIP: what it takes to run inside a real insurer

Research and gap analysis, 2026-10-05. Verified against the code on `main` (`d5e9bed`) and the dev environment. Web findings are cited at the end; anything not confirmed is marked **to verify**.

## Bottom line

IIP works today as a standalone claims workspace with its own WhatsApp front door. What stops a Ugandan insurer from running it for real is not the AI or the screens. It is three things:

1. **It does not yet talk to the insurer's own systems.** Policies come from a CSV import or a generic REST adapter that no real core system has been connected to. Nothing flows back: no claim, payment or reserve reaches the core system, finance or the IRA returns.
2. **The operational controls a regulated buyer's IT and risk teams will ask for are partly there, partly missing:** single sign-on with their directory, backups and recovery they can test, a hosting region they can justify, a durable message queue, evidence for an IT due-diligence questionnaire.
3. **No packaged way in.** Each integration today would be bespoke work.

The way to make integration a no-brainer is to make IIP useful on day one with **no** integration, then offer integration in small, optional steps, with pre-built adapters for the two core systems most insurers in the region run.

## 1. What a Ugandan insurer actually runs

| System | What is known | Why IIP needs it |
|---|---|---|
| **Core insurance system** (policy admin, claims register, premiums) | Common vendors in the region: **TurnQuest** (Turnkey Africa, 42 clients in 7 African countries) and **Premia** (3i Infotech, 50+ African customers including Uganda). Smaller insurers often run in-house systems or spreadsheets. Which insurer runs which is **to verify** per prospect. | Source of truth for policies, cover, premiums paid; destination for claims and payments. |
| **IRA reporting** | IRA requires automated filing of returns since 1 July 2023, with monthly, quarterly and annual templates (premiums, claims, HMO). ESG reporting guidelines published April 2026. | Claims data feeds these returns. If IIP holds claims, it must export in the shape the returns need. |
| **Motor third-party register** | Since 1 October 2025 motor third-party certificates are digital only, issued against the vehicle registration into a central database (IRA, Uganda Insurers Association, Traffic Police; URA and Works and Transport on a shared platform). | Verify a motor policy and vehicle at claim time; later, issue third-party cover. Access terms **to verify** with IRA/UIA. |
| **Mobile money** | MTN MoMo and Airtel Money are the premium rails (e.g. Cover by MoMo with Sanlam; Britam with Airtel Money); aggregators such as NxtPe serve insurers. | Collect microinsurance premiums; pay approved claims to the policy's phone. |
| **Medical claims (HMOs)** | Medical cover runs through HMOs and administrators such as Smart Applications, connected to hundreds of health facilities. | Medical claims mostly arrive through these, not WhatsApp; IIP should receive them, not replace them. |
| **Finance / general ledger** | Usually separate (e.g. Sage, Dynamics, Sun). **To verify** per insurer. | Approved payments and reserves must post here. |
| **Staff directory** | Microsoft 365 / Entra is common; some Google Workspace. | Single sign-on and joiners/leavers. |
| **Documents and email** | Shared mailboxes, SharePoint or file shares. | Claims documents already live here. |

## 3. Making integration a no-brainer

Insurers say yes when the first step costs them nothing and each later step is small and reversible. A ladder:

**Rung 0: no integration (day one).** Value without touching their systems.
- Policies loaded from the spreadsheet export every core system can produce (exists; add saved column mappings for TurnQuest and Premia exports so it is one click).
- Claims arrive by WhatsApp, email and the portal; staff work them in IIP.
- Daily claims export in a spreadsheet their team or the IRA return already uses (to build).

**Rung 1: read-only connection.** IIP looks up live policy and premium status.
- Pre-built **TurnQuest** and **Premia** adapters on top of the generic adapter. These need vendor API documentation, which normally comes through a partnership or the insurer's own licence (**to verify** with each vendor).
- For systems with no API: a read-only database view or a scheduled file drop (SFTP) that IIP picks up. Most legacy cores can do one of these.

**Rung 2: write-back.** IIP sends decisions to the systems that own them.
- Outbound events (claim registered, documents complete, decision approved, payment approved) as signed webhooks and as a file feed, so the insurer's IT or vendor can consume them however suits them.
- Payment instruction to mobile money after a named person's approval.

**Rung 3: full workflow.** Claim registration and payment flow straight into the core system; IRA return figures come out of IIP.

What makes every rung easy:
- **One published data contract** (policy, customer, claim, payment, document) with an OpenAPI spec, sample payloads and a sandbox tenant.
- **A connections screen per system** with "test connection" and live health, as SMS and translation already have.
- **A field-mapping screen**, so a new export layout is configuration, not code.
- **Partnerships with Turnkey and 3i Infotech**: a listed adapter is the real "no-brainer".

## 4. Gaps by area

| Area | Today | Gap to close |
|---|---|---|
| **Integration** | Generic REST read adapter, CSV import, channels. | Vendor adapters (TurnQuest, Premia), file-drop/SFTP and DB-view options, outbound signed webhooks, claims/payment export, mobile money, motor register lookup, HMO intake, finance posting. |
| **Data** | Every record scoped by tenant and workspace; JSON-stored entities with relational customers. | Published canonical data model; data dictionary; reconciliation report (IIP vs core system); retention rules per data class already partly built; data quality checks on import. |
| **Cybersecurity** | Entra auth, membership-based authorisation, encrypted connection secrets, signed WhatsApp webhooks, magic-link portal, secrets write-only from browser. | Encryption keys for stored credentials are not in Key Vault; no web application firewall or rate limiting on public endpoints; no penetration test; no published security pack (controls, architecture, incident contacts). Bank of Uganda's 2024 cyber guidelines are a good benchmark for what an insurer's risk team will ask, even though they bind banks. |
| **Privacy** | Data-subject export, rectification and erasure; consent records for WhatsApp; retention enforcement. | Otic's PDPO registration as a data processor (annual renewal); data processing agreement template for insurers; records of cross-border transfer basis (dev is hosted in West US 2; the DPPA allows transfer with consent or adequate protection, but records must be kept); privacy notice shown to WhatsApp customers; sub-processor list (Microsoft, Meta, Sunbird). |
| **Governance** | Human-decision boundary in code and prompts; immutable platform preamble; agent kill switch; role-based permissions. | Model risk documentation for Kato (purpose, limits, testing, monitoring); named owner per insurer for AI behaviour changes; quarterly review of AI outcomes; IRA product approval references for real products (demo products are labelled not approved). |
| **Infrastructure** | Azure App Service, Azure SQL (Standard, geo-redundant backups), AI Search, Azure OpenAI; infra as code in `infra/`. | Hosting region decision (South Africa North is the nearest Azure region; Uganda has none); separate production environment; private networking for SQL and storage. |
| **Reliability** | Single API instance; WhatsApp assistant uses an in-memory queue; model failure falls back to rule-based replies. | Durable queue (Service Bus is already used for other work) so a restart never loses a customer message; at least two instances; retry and circuit-breaker on external calls; deploys without downtime (staging slot). Today's field test showed a deploy takes Kato offline for minutes. |
| **Observability** | Application Insights connected; audit events; delivery states on WhatsApp messages. | Per-tenant dashboards (messages, replies, response time, failures, AI cost); alerts on reply time and failure rate; end-to-end timing of each customer message (the 13-second unexplained delay before a message reaches IIP). |
| **Auditability** | Every consequential action audited with actor, reason and correlation id; AI suggestions recorded separately from human decisions. | Audit export for an auditor or the IRA; tamper-evidence (write-once storage or hash chain); retention period agreed per insurer. |
| **Human control** | AI never approves, pays or binds; claims filed only after the customer confirms; approvals by named people. | **Field-test exception to retire before production:** demo applications are issued as policies immediately on the demo phone. Production must route every application to a licensed person. Configurable approval limits per insurer (who can approve what amount). |
| **Operational resilience** | Geo-redundant database backups (platform default). | Tested restore; recovery time and recovery point targets written down; incident response plan with insurer notification times; exit plan (full data export if an insurer leaves). |
| **Change management** | Git, CI, tests (1,655), deployment runbook. | Release notes per insurer; change windows agreed with insurers; staging that mirrors production; versioned API so integrations do not break; AI prompt and behaviour changes treated as releases. |
| **Applicable regulation** | Microinsurance guidelines reflected in demo products; human decisions preserved. | **To verify with IRA:** rules on outsourcing and cloud for insurers (none found published); whether Otic needs any IRA registration as a technology provider; electronic records and signatures (Electronic Transactions Act 2011) for claims evidence; Anti-Money Laundering checks on payouts; ESG reporting (2026) data needs. |

## 5. Suggested order for the "insurer-ready" build

1. **Rung 0 integration:** saved import mappings for TurnQuest and Premia exports, claims export, IRA-return-shaped claims report.
2. **Reliability floor:** durable queue for WhatsApp, two instances, zero-downtime deploys.
3. **Security and privacy pack:** Key Vault for keys, rate limiting, PDPO registration, data processing agreement, sub-processor list, hosting region decision.
4. **Outbound events and mobile money payouts** (after named approval).
5. **Vendor adapters** once a partnership or a pilot insurer's API access is in hand.
6. **Observability per tenant** and the audit export.
7. Then continue the SaaS build, which multiplies all of the above across insurers.

## 6. To verify before committing

- Which core system each target insurer runs, and what interface it exposes (API, database, file export).
- Whether Turnkey Africa and 3i Infotech offer partner API programmes.
- IRA requirements for insurers outsourcing IT or using cloud services, and any registration for technology providers.
- Access to the motor third-party central database for claims verification.
- Hosting region acceptable to target insurers and the PDPO.
