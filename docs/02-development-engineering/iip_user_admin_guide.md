A response may contain:

- a short explanation;
- metric pills;
- a claim table;
- a missing document list;

- an action proposal;

Users must remember:

- AI summaries are assistance, not final decisions.
- AI cannot approve or reject claims.
- AI cannot accuse a customer, broker, hospital, garage, or staff member of fraud.

- Customer-facing messages generated by AI must be reviewed where required.
- Evidence and confidence should be checked before acting.

This guide explains how to use and administer the **Insurance Intelligence Platform (IIP)**.

IIP is an Azure-native, human-reviewed insurance operations platform that helps insurers acquire customers, process claims, review documents, support underwriting, manage customer interactions, and maintain auditable workflows through AI-assisted, source-grounded, role-aware workspaces.

This guide is split into two major parts:

1. **User Guide** - for day-to-day insurer users such as claims officers, supervisors, customer service agents, underwriters, compliance officers, and executives.
2. **Admin Guide** - for insurer admins, IT admins, compliance admins, platform admins, and implementation teams responsible for configuring, securing, monitoring, and supporting IIP.

This document is not a marketing brochure. It is an operating guide for people who will use, configure, support, or demonstrate the platform.

## 2. Core Product Principles

IIP must always follow these principles:

| Principle | Meaning |
|---|---|
| Human-reviewed insurance intelligence | AI prepares work, but people make regulated decisions. |
| Evidence-first | AI outputs must be connected to claim data, documents, knowledge base items, or approved workflows. |
| Tenant-aware | Every case, customer, document, conversation, task, lead, and audit event belongs to a tenant and workspace. |
| Role-aware | Users only see the screens, records, and actions allowed by their role. |
| No autonomous regulated decisions | IIP must not approve, reject, bind, settle, price, accuse, or release payment without human approval. |
| Internal workspace first | Customers do not log into the internal insurer workspace. External interactions feed internal work queues. |
| Microsoft-native | The platform is designed around Azure, Microsoft Entra ID, Microsoft Graph, Azure AI, Azure SQL, Azure Blob Storage, and Azure monitoring services. |
| Audit by design | User actions, AI actions, approvals, overrides, documents, and integrations must be logged. |

## 3. What IIP Is and Is Not

### 3.1 What IIP Is

IIP is an insurance operations command center that helps insurer teams:

- Receive and triage customer conversations from channels such as WhatsApp, WebChat, SMS, email, broker uploads, website forms, and call center inputs.
- Convert customer conversations into leads, claims, tasks, or service work items.
- Capture First Notice of Loss (FNOL) information.
- Upload, classify, extract, and validate insurance documents.
- Generate human-reviewable claim summaries.
- Detect missing documents and possible inconsistency or fraud signals.
- Search approved insurance knowledge such as policies, claim rules, SOPs, FAQs, and underwriting guidelines.
- Draft customer-safe messages for human review.
- Route work to the correct officer, supervisor, team, or approval queue.
- Track SLA risk, pending approvals, customer updates, and audit evidence.
- Maintain a clear audit trail for compliance and operational review.

### 3.2 What IIP Is Not

IIP is not:

- A replacement for the insurer's core policy administration system.
- A replacement for a claims officer, underwriter, compliance officer, broker, or executive.
- A generic chatbot added onto an insurance dashboard.
- A tool that can autonomously approve or reject claims.
- A tool that can autonomously bind policies, price premiums, accuse a customer of fraud, or release payment.
- A customer-facing portal in its internal workspace form.

# Part A - User Guide

## 5. Getting Started

### 5.1 Logging In

Users access IIP through the insurer's configured identity provider, normally Microsoft Entra ID.

Default expected login behavior:

1. Open the IIP web application URL.
2. Select the insurer workspace or tenant if prompted.
3. Sign in using the approved organization account.
4. Complete MFA if required.
5. Land on the role-specific Command Center.

If login fails, the user should see a safe error message that does not expose sensitive system details.

### 5.2 Tenant and Workspace Context

Each user works inside a tenant and workspace context.

Examples of workspace segmentation:

- Claims workspace
- Sales and leads workspace
- Customer service workspace
- Health claims workspace
- Motor claims workspace
- Branch or region workspace
- Country workspace
- Broker network workspace

Users should always be able to confirm:

- Which insurer tenant they are working in.
- Which workspace they are using.
- Which environment they are in: development, staging, demo, or production.
- Which role is active.

### 5.3 Production Safety

In staging or production:

- Do not use mock data as real records.
- Do not bypass authentication.
- Do not use fake endpoints as if they are working integrations.
- Empty API responses should show empty states.
- Failed API calls should show error states.
- Not configured providers should show a clear `Not configured` state.

### 11.5 Claim Review Pattern

A claim review should follow this pattern:

```text
Open claim
-> Review AI summary
-> Review customer and policy details
-> Review documents received
-> Review missing documents
-> Review extracted fields and confidence
-> Review fraud or inconsistency signals
-> Review policy references and evidence
-> Add note or correction
-> Approve next workflow step, escalate, or request more information
-> Confirm audit trail
```

### 11.6 What AI Can Do in Claims

AI may:

- Summarize claim details.
- Classify documents.
- Extract fields.
- Flag missing documents.
- Highlight inconsistencies.
- Draft customer-safe requests.
- Suggest next review steps.
- Search policy and claims knowledge.
- Prepare an evidence pack.

AI must not:

- Approve claims.
- Reject claims.
- Promise settlement.
- Set final settlement amount.
- Accuse a customer of fraud.
- Release payment.
- Hide uncertainty.
- Override a human decision.

## 12. FNOL / New Claim Intake

### 12.1 Purpose

FNOL means First Notice of Loss. It is the point where a customer, broker, agent, or staff member first reports a claim.

IIP should support FNOL through:

- WhatsApp.
- Email.
- Website form.
- Broker upload.
- Call center entry.
- Manual internal staff entry.

### 12.2 Intake Fields

Default FNOL fields:

| Field | Notes |
|---|---|
| Customer name | Required where known. |
| Contact details | Phone/email/channel reference. |
| Policy number | Required where available. |
| Claim type | Motor, health, life, property, etc. |
| Incident date and time | Required for motor claims. |
| Incident location | Required for motor claims. |
| Incident description | Customer or staff narrative. |
| Vehicle registration | Required for motor claims. |
| Driver details | Required where applicable. |
| Third-party details | Required where applicable. |
| Documents received | Auto-linked as uploaded. |
| Consent confirmation | Required for data processing. |

### 12.3 Intake Completion

A claim should not be treated as complete until:

- Required FNOL fields are captured or marked unknown.
- Required documents are uploaded or listed as missing.
- Customer consent is captured where required.
- The claim has a unique reference.
- The claim is routed to the appropriate queue.

## 34. Common Troubleshooting

### 34.1 User Cannot Log In

Check:

- User exists in identity provider.
- User has been invited to IIP.
- User has tenant/workspace access.
- MFA is complete.
- Browser session is not stale.
- App registration and redirect URI are correct.

### 34.2 User Cannot See a Claim

Check:

- Tenant ID.
- Workspace ID.
- Role permissions.
- Assignment rules.
- Branch/product restrictions.
- Claim status restrictions.

### 34.3 AI Answer Looks Wrong

User should:

1. Check source citations.
2. Check confidence level.
3. Verify the approved knowledge source.
4. Correct the output if permitted.
5. Escalate if the answer affects a customer or regulated decision.
6. Log the issue for AI quality review.

### 34.4 Document Extraction Failed

Check:

- Document quality.
- Document type.
- File format.
- File size.
- Document Intelligence provider health.
- Template configuration.
- Confidence threshold.
- Queue status.

### 34.5 WhatsApp Messages Not Arriving

Check:

- Provider health.
- Webhook status.
- Verification token.
- Message queue.
- Failed events.
- Provider credentials.
- Network/connectivity issue.
- Channel configuration status.

### 34.6 Integration Shows Not Configured

This usually means the provider has not been configured or credentials are missing. Admins should configure the provider or leave the state visible as `Not configured`; do not hide it behind fake data.

## 37. Final Operating Rules

1. Use **Insurance Intelligence Platform (IIP)** as the official name.
2. Treat ACIP as a superseded naming direction.
3. Keep customers out of the internal insurer workspace unless a separate customer-safe portal is explicitly built.
4. Use WhatsApp and other channels as external intake paths feeding internal work queues.
5. Use Motor Claims and Document Intelligence as the first MVP workflow.
6. Keep AI evidence-grounded, confidence-aware, and human-reviewed.
7. Do not allow AI to make final regulated insurance decisions.
8. Do not hide missing integrations with mock production behavior.
9. Log all important actions.
10. Keep tenant and workspace boundaries strict.
11. Use approved knowledge for policy answers.
12. Escalate uncertainty, conflicting evidence, low confidence, and sensitive outcomes.
