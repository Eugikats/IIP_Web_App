## Scope and status rules

This is an evidence-backed code audit of the master prompt journeys. Statuses distinguish code from an end-to-end result:

- **Implemented and verified** means the behavior has a passing focused automated or protected-environment end-to-end check.
- **Code present but unproven** means a substantive implementation exists, but this audit has not established the complete journey or live provider result.
- **Partial** means a related slice exists but a required user outcome or safety/operational seam is missing.
- **Documented only** means the repository describes the target but does not implement it.
- **Absent** means no relevant implementation was found in this audit.
- **Blocked by external configuration** means code exists and a named external registration, credential, approval, or decision is required for the dependent proof.

No production/provider capability is called complete based on mocks, endpoints, screenshots, or plans.

## First acquisition demo sequence

1. Authorized staff admin signs in; server resolves insurer and workspace. 2. Admin selects the approved product version and WhatsApp sender/template. 3. Staff imports a small permitted CSV/XLSX; mapping, duplicates, fit factors and exclusions are reviewed. 4. Contact purpose/consent evidence is checked; a workbook boolean alone cannot establish permission. 5. Reviewer inspects the exact recipient set, rendered placeholders, product/template versions, limits and sending window; approval binds to that snapshot. 6. Dispatch rechecks opt-outs, consent, template approval, tenant, provider health and idempotency. 7. The system records provider accepted/delivered/failed/unknown separately. 8. Reply appears in the same tenant's Inbox and prospect timeline; Kato answers only from approved product evidence. 9. Customer requests a person; staff takes over. STOP suppresses any queued follow-up. 10. Staff sees the outcome and campaign denominator in real, persisted reporting.

**Current gate:** workbook analysis exists, but the code itself says sending from this analysis is not connected and Meta approval is unverified (`web/portal/components/workspace/KatoWorkspace.tsx`; `WorkbookProspectAnalyzer.cs`). Do not present this journey as complete until a configured approved test send and inbound reply are observed.

## Motor claims journey sequence

1. Customer/staff submits motor own-damage FNOL; API resolves tenant and creates a case. 2. Product/claim context selects relevant document requirements; customer gets a secure request/link. 3. Original files are stored and extraction status progresses through real provider states. 4. Field groups show values, confidence and source page/region; uncertain values remain proposals. 5. Reviewer corrects/accepts/rejects fields with before/after audit; change invalidates downstream summaries. 6. A case insight is prepared from current policy and claim evidence with citations, caveats and missing items. 7. Authorized claims staff makes any consequential decision; customer update is separately reviewed/approved. 8. Evidence pack exports original references, extracted/corrected values, source versions, citations and audit. 9. Outage, unknown provider response and retry remain visible and never produce fabricated completeness.

## Changes made during this audit

- `src/InsuranceIntelligence.Domain/Acquisition/Outreach.cs` now distinguishes WhatsApp provider-accepted, delivered and unresolved outcomes.
- `src/InsuranceIntelligence.Application/SalesLeads/OutreachService.cs` now preserves those outcomes, labels them clearly, audits the actual state, and prevents another send or edit while an accepted, delivered, or unresolved outcome is in progress. This closes the previously misleading “Unknown becomes Sent” state.
- The same service now checks the persisted WhatsApp message status before reporting a previously accepted/unknown outcome. A delivery receipt can resolve it to delivered or failed; a known failed send requires another explicit staff action before retry. A still-unknown result stays blocked from duplicate sends.
- `web/portal/components/acquisition/tabs/OutreachTab.tsx`, `web/portal/lib/lovable-parity/data/salesLeads.ts`, and `web/portal/lovable-pages/CustomerAcquisition.tsx` display the new states and offer “Check delivery status” instead of implying delivery or offering a duplicate send.

- Verification is pending because the .NET test assets are absent. Restore/build requires additional free disk space; the portal test suite does not cover this backend change.
