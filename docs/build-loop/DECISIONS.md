# Decisions

Judgement calls made without asking, most recent last.

## D-001 Branch base
The prompt says branch from `origin/main`. The audited code (and the 1764-test baseline) is the current local branch `feature/bancassurance-acquisition` at `e8b2b42`, which is 28 commits ahead of `origin/main` and 0 behind, and contains work the audit describes (Kato agent, Academy, document type catalogue, claim intake). Branching from `origin/main` would drop it and make the audit and baseline wrong. Decision: `build/claims-core` is branched from `e8b2b42` (committed state only; the original working tree's uncommitted changes are untouched). Consequence: pushing `build/claims-core` also publishes those 28 commits to origin as part of the new branch.

## D-002 Pushing is blocked by the environment
The auto-mode permission classifier denied `git push -u origin build/claims-core` (external system write; it would also publish the 28 pre-existing local commits to origin). I did not work around it. All work is committed locally on `build/claims-core` in `../iip-build`; the push must be run by a human (`git -C ../iip-build push -u origin build/claims-core`). Every item's "push" step is therefore skipped and noted here once, not per item.

## D-003 Mock providers live in Api/Local, not LocalTestDoubles
The prompt says to reuse `LocalTestDoubles`. `InsuranceIntelligence.Api` deliberately does not reference that project (AGENTS.md: it never ships in or activates in protected runtimes), and `Api/Local/` already holds shipped dev-only mocks (`MockTranslationProvider`, `LocalMockDocumentStorageProvider`). New Mock providers are therefore added under `src/InsuranceIntelligence.Api/Local/Mock/`, reusing the logic and wording of the LocalTestDoubles mocks but not referencing the project. Protected runtimes are already refused by `AzureProviderStartupValidator.ValidateProduction` for every `*_PROVIDER` setting equal to `Mock`.

## D-004 Provider health: new "mock" status, three existing tests changed on purpose
Item 1 requires that an unconfigured or mock provider is never shown as "Operational". `AdminEndpoints.BuildProviderHealth` now reports `mock` (not `healthy`) for any provider set to Mock under Development auth, reports the Teams notification provider as `not_configured` when set to Mock (no Mock Teams adapter exists, so it was never working), and the overall status is `degraded` if anything is missing/not configured, else `mock` if any mock is active, else `healthy`. The portal maps `mock` to the warning tone with the label "Mock". The email-integration health overall status now considers only `graphMail` and `communications` (Teams stays listed but no longer degrades email health).
Tests changed because behaviour changed on purpose (not weakened): `Phase7ProviderTests.ProviderHealth_ReturnsMockProvidersHealthyWithoutSecrets` (renamed `..AsMockWithoutSecrets`, now asserts `mock` and `degraded`), `Phase7ProviderTests.ProviderStatus_ReturnsSafeOperationalProviderStripShape` (overall `degraded`). `Phase6IntegrationTests.EmailIntegrationHealth_ReportsConfiguredGraphActionsWithoutSecrets` passes unchanged after the email-scope change.

## D-005 Mock marker for fixtures
The mock document provider classifies from the ASCII marker `IIP-MOCK-DOC:<Type>` anywhere in the first 4 MB of a file, and plants fields with `IIP-MOCK-FIELD:key=value`. Fixture files under `web/portal/tests/fixtures/claims-core/` carry the marker appended after the image/PDF payload (decoders ignore trailing bytes). With no marker, whole-token file-name matching applies (so "accident_report.pdf" is not a customer ID).

## D-009 Item 3 judgement calls
- Claim types are part of the product version snapshot (not a separate table), so versioning, publishing approval and claim pinning work unchanged and old claims keep their meaning.
- Enforcement is by form, not by channel: staff and claimant forms must pick a configured active type when the product has any; email and WhatsApp (and Kato) cannot ask, so they get a best guess from the description (never a decision) and a person confirms it when confirming the claim. A retired type still resolves for history but cannot be chosen for a new claim.
- Suggestion stems words to their first five letters ("stole" meets "stolen"); it returns nothing rather than guess when two types tie.
- `ClaimTypeClassifier` (Motor-only keyword routing) is kept: `ClaimRoutingPolicy` still reads the claim type text, and claims on products with no configured types need it.
- Existing free-text claims are migrated explicitly (button/endpoint), not silently on read, so nothing changes without a person asking and the result is audited as a new product version.

## D-010 Item 4 judgement calls
- The same document key may appear more than once when each entry names different claim types, or as one "every type" entry plus type-specific ones; the type-specific entry wins for those types. Two entries that would apply to the same claim type at the same level are refused.
- A configured matrix with nothing for a claim type returns an empty requirement set rather than falling back to the built-in Motor rules: it is the insurer's answer, the editor warns about it, and completeness reads 100% because nothing is required. A product with no matrix at all keeps the built-in rules.
- A stored requirement with no kind takes the default for its document (photos of the damage are Evidence, everything else Document); this avoids a data migration and keeps seeded products correct.
- Plain text is not an accepted customer format for any slot (PDF and images only); tests that used .txt for slot uploads use .pdf names, the mock provider reads the marker from the bytes either way. Staff upload still accepts text as before.
- Customer wording: both the customer page and the staff checklist now use the product's own label for built-in documents (the hard-coded label table in the claimant endpoints is gone), which also delivers the B2 part of item 6.
- The follow-through reminder timer previously used only the built-in rules (a recorded shortcut). It now uses the shared product-aware provider in both hosts, so a reminder asks for the documents the customer's own page asks for.
- Removing a single file from a multi-file slot is not part of this item; "Remove" still clears the slot (item 12 adds per-file removal with the page flow).

## D-011 Item 5 judgement calls
- Fields are part of the product version snapshot (like claim types and the document matrix), not a separate table.
- Built-in definitions use the FNOL record property names as keys and are what a new Motor or Medical product starts with; the original hard-coded staff form remains only as the fallback for a product with no configured questions, so nothing regresses. The medical built-ins are the original nine minus the free-text "uploaded documents note" (documents have their own slots).
- Original FNOL answers sent by older clients count as present for required questions but are not type-checked (they used free wording such as Yes/No where the built-in choice list says "Injury reported").
- Staff-only questions are for staff to answer; a claimant cannot read or write them. A claimant cannot be required to answer a staff-only question.
- Field answers live in `ClaimCase.FieldValues` as strings; per-answer provenance (who or what supplied it, whether a person confirmed it) is added by item 15 as a parallel record rather than changing this shape.
- The audit event for saving answers records the field keys only, never the values (they can be personal).

## D-012 Item 6 judgement calls
- Operating values live in one `TenantSettings` row per workspace with typed columns (not a key/value bag), so each has a validated range and a default equal to the old constant. A workspace with no row is read as the defaults and no row is written until an administrator saves.
- Settings are optional constructor dependencies of the services that use them, so Functions and tests that build those services directly keep the old behaviour.
- The IRA rule removes only the IRA reference and effective date requirement. A product still needs a lifecycle and a second approver to publish.
- Seat limit and claims allowance are shown on the billing page only. Enforcing them is item 32 (plans, limits and payments).

## D-013 Item 7 judgement calls
- The wording text is the stored knowledge chunks joined in order (the same text the search index holds), not a re-read of the original file, so a PDF or Word wording is only as readable as its extraction. Pages come from form feeds in the extracted text, or a "Page N" line; when neither exists the page is blank and the clause number still shows.
- A quote that cannot be found in the wording is kept, flagged and not acceptable (rather than dropped), so the reviewer sees what the model claimed. A quote needs at least 12 letters to count as found.
- Documents may only use an existing document type (the built-in ones plus the workspace catalogue); the model is given the list and a miss blocks acceptance until a person picks one. Creating new document types from a wording is left to the document type catalogue screen.
- Applying is additive and never edits existing configuration. A product with no questions of its own gets the built-in questions kept alongside the new one, because an empty list means "use the built-ins".
- Documents are required at the "Acknowledgement and document request" stage when the product has it, else its first stage; this can be changed on the matrix afterwards.
- Covered and excluded items are informational (staff reference and later grounding); they never decide a claim, in line with the human-decision rule.
- The model call uses the shared chat provider with no tenant agent profile; no prompt text is stored, only the proposals.

## D-014 Item 8 judgement calls
- The preview endpoint is a read and writes no audit event (like the other configuration reads); it creates no claim, no communication and no consent.
- The claimant form and documents card were extracted from the two claimant pages into shared components rather than copied into the preview, because items 9, 10, 12 to 14 (consent, capture, scanner) change these exact screens and the preview must follow them.
- Sample values: the policy number is POL-SAMPLE-0001 and the incident text is a marked sample; no real customer data is ever read.
- A product with no configured claim types previews the built-in rules for its product line, matching what a claim on it would get.

## D-015 Item 9 judgement calls
- Consent is per claimant contact (the verified email or phone they signed in with, normalised), not per claim: someone who agreed on one claim is not asked again on the next unless the notice changed. It lives in the existing append-only consent store with purpose `claim_data_processing` and a `NoticeVersion`, so there is one consent history, not a second one.
- The gate is on the claimant portal upload only. Staff uploading on a customer's behalf, and WhatsApp documents (which rest on the WhatsApp contact consent), are not gated by this notice; item 21 and 27 revisit those channels.
- Withdrawal blocks new portal uploads and nothing else. It does not delete or hide documents already sent; retention, deletion and erasure are item 34.
- The default notice text is a plain-language draft, **to be confirmed by legal** before an insurer relies on it. The settings page says so; the customer page does not show that marker.
- Existing tests that upload as a claimant were changed on purpose: the integration helper `TestData.ClaimantClientAsync` now agrees to the notice through the real endpoint (opt out with `agreeToPrivacyNotice: false`), six direct-call unit tests of the upload handler pass a stub that has already consented, and the e2e helper `openClaimantPortal` presses "I agree" unless told not to. Their intent (what happens to an upload) is unchanged; consent has its own tests.
- A consent record's `RecordedByUserId` is the normalised claimant identifier, never the raw email or phone.

## D-016 Item 10 judgement calls
- The camera input is a separate file input with `capture="environment"` rather than one input with a mode switch: it is the only reliable way to open the rear camera directly on iOS and Android browsers, and it keeps "choose several files" working on the other input.
- The camera button is offered when a slot accepts any image format (or has no format list) and hidden when it accepts none. Whether the file a phone camera produces is accepted still depends on the slot's formats; HEIC handling is item 11.
- Existing e2e tests used the one file input of a row; they now target `input[data-upload="choose"]` because a row has two inputs. Selector change only, not behaviour.

## D-017 Item 11 judgement calls
- Library: **Magick.NET-Q8-AnyCPU 14.17.1** (Apache-2.0, ImageMagick native code, runs in process, no network) in the Api project, behind `IImageDerivativeProvider`. Chosen over ImageSharp (Six Labors split licence needs a commercial licence for many businesses) and SkiaSharp (no HEIC decode). It decodes HEIC but cannot encode it, so the HEIC test fixture was made once with pillow-heif (a test-time tool only, not shipped).
- The hash is over the bytes as received by the API. The browser path is verified by comparing it with the hash of the chosen file; there is no separate client-side hash, because a client-computed hash would be unverifiable by definition.
- The preview strips all metadata on purpose: staff look at the preview, while the untouched original (with EXIF) is what item 16 inspects for authenticity.
- Previews are made for every picture, evidence or paperwork, because staff need to see HEIC either way. They are never used as the evidence.
- Staff uploads are no longer compressed in the browser: the original is what is kept and examined. The older second client compressor (`compressImageForUpload`) was deleted; its only caller was that staff widget.
- Decoding limits (16,000 px per side, 120 million pixels, 512 MB, 20 seconds) are process-wide Magick limits set when the provider first loads.

## D-018 Item 12 judgement calls
- The PDF is built with Magick.NET (already added in item 11), which writes PDF without Ghostscript: each picture is turned upright, limited to about A4 at 200 dpi and written as a JPEG-compressed page. A separate PDF library was not added. Reading PDFs back would need Ghostscript, so tests check the page boxes in the PDF bytes instead.
- A slot's PDF exists only when every active file in it is a picture. A mix of a PDF and photos, or a lone PDF, is left as the files were sent rather than guessing how to merge them. Merging an existing PDF with photos can be added with a PDF library later if wanted.
- Page order is explicit (`PageOrder`) once the customer arranges pages, otherwise upload order. Removing a page keeps its file (superseded) like every other removal.
- The PDF is rebuilt in the request that changes the slot (a few pages, a second or two). It is not queued: item 17 introduces the durable background pipeline, and a build failure here already degrades safely to "no combined PDF".
- Old PDFs stay in storage as history (each rebuild writes a new derived object); the record points at the current one. Retention of derived copies belongs to item 34.

## D-020 Item 13 judgement calls
- The scanner is plain TypeScript image maths rather than OpenCV.js: no multi-megabyte download on a paid data bundle, no licence to track, and the maths is small enough to test on fixtures. The trade-off is that page detection assumes a page clearly lighter or darker than its background and roughly upright; when that fails it says so and the person drags the corners, which is the designed path, not an error.
- Scanner output is limited to about A4 at 200 dpi (short side 1600 px), which also keeps it under the browser compressor limit, so a scan is not recompressed again before sending.
- Fallback never shows a dead end: any failure hands the customer the plain camera for that slot, because the point of the scanner is convenience, not a new way to be blocked. Browsers may refuse to open a file chooser programmatically after a long permission prompt; in that case the sentence tells the customer to press Take photo.
- Not covered by tests: a real phone camera and real lighting. The tests use a stand-in camera that draws a skewed page, so the real-device behaviour is a manual check (item 13 walkthrough step 1 to 3).

## D-021 Item 14 judgement calls
- Recognition runs against the workspace catalogue, not only the eight built-in types, but only for what the recogniser can read: the real adapter reads pictures (JPEG, PNG, HEIC, TIFF through the preview) and reports a PDF as "a person will look", because rendering a PDF page to an image needs a PDF renderer that is not in the product yet. Local Mock recognises by marker or label text so it can be tested end to end. This is an honest limitation to close with Document Intelligence text in item 15 if wanted.
- The threshold for "confident" is 0.8, in one place (`DocumentRecognition.ConfidentThreshold`).
- The existing built-in classifier (`Classification`) is kept and still used as the second opinion when the recogniser is not confident, so staff-flag behaviour from item 2 is unchanged when no recogniser is available.
- The recognition outcome is audited by type and confidence only, never the content. The system actor is `system`; filing by a person is audited with their id.
- Staff uploads now also pass through recognition (their files used to be unnamed and unplaced). A file filed automatically can always be moved by a person.
- WhatsApp and email attachments are recognised and named too; they are filed into a slot only when clear, as above. Customers are not told anything about this beyond their documents appearing as received.

## D-022 Item 15 judgement calls
- Values come from the provider's own extraction (Document Intelligence in Azure, the Mock locally) mapped by the insurer's reading rules. A separate model pass over the text was not added: the real provider already returns named fields with confidence and page, and a model-guessed value would be less checkable than a field the provider read. The rules make any named field usable; a model-based reader can be added behind the same proposal path later.
- "Person-confirmed" is every answer a person put on the claim: the customer's own answer, an officer's edit, or an accepted proposal. Answers with no provenance (stored before this item) are treated the same, so no old answer can be overwritten silently.
- Built-in defaults are limited to the medical report because every other built-in mapping depends on the insurer's own questions; guessing a mapping would put wrong data on claims. Insurers set the rest with their own rules.
- The reading rules are configurable through the existing document type API only; the product has no document type administration screen yet, so there is no UI for it. This is a gap to close when the catalogue gets a screen (noted for the final summary).
- The Mock extraction returns fixed values per document type (for example report number MOCK-POL-0001), which is what the tests and walkthrough use; real providers return what is on the page.

## D-023 Item 16 judgement calls
- Findings are prompts, never scores or verdicts, and nothing is blocked. Severities are fixed in `AuthenticityRules` in one place; the High ones are the two that are hard to explain innocently (a photo older than the incident, and the same picture on another claim).
- A photo with no EXIF is only Low for evidence photos: messaging apps (WhatsApp, Telegram) strip metadata from every photo, and this product receives many photos that way. Paperwork is not expected to carry camera details.
- Duplicate search is workspace-wide among pictures that have been analysed (indexed on workspace and hash), comparing 64-bit difference hashes with a distance of 4 or less. A later copy is flagged against the earlier one; the earlier one is not re-flagged retroactively. The comparison reads all hashed reports in the workspace; item 35 (scale) replaces that scan with a bucketed lookup.
- No AI is used here (no model sees the picture), so there is nothing to Mock; the analysis runs in process with Magick.NET behind `IImageForensicsReader`. Signs of editing are therefore metadata signals, not pixel forensics; detecting pasted or generated regions would need a specialist model and is left out on purpose rather than faked.
- Staff-uploaded pictures count as evidence only when filed in an evidence slot; an unslotted staff upload is treated as paperwork for the "no camera details" nudge.

## D-024 Item 17 judgement calls and the parts not built
- **Durable store, not Service Bus.** The brief asks for "a Service Bus consumer in Azure, a durable local equivalent in Mock mode". I built one durable queue in the database used in every environment (lease, retry, dead letter, visibility), because it is atomic with the data it works on, runs identically locally and in Azure, and works across several API instances (optimistic lease token on SQL Server). A Service Bus consumer would add scale-out and cross-service fan-out but cannot be proven here without an Azure namespace, so it is left as a swap-in behind the same handlers and is listed in the real-credentials checklist. `IMessageQueueDispatcher` is unchanged.
- **Two in-process queues remain.** The WhatsApp assistant queue stays in memory for now: moving it means redesigning how an inbound message is replayed without storing customer words in a job, and item 27 (multi-tenant WhatsApp) reshapes exactly that webhook; making it durable is an explicit part of item 27. The conversation-insights queue is derived analytics that can be recomputed on demand, so losing a pending refresh at restart costs nothing.
- Everything is in one handler per document (read, name, extract, check, offer values) run in sequence, not four parallel jobs: documents run in parallel with each other across workers, and the steps share one read of the file. Splitting the steps into separate jobs is an option when a step needs its own scaling.
- The claim review runs the existing claims summary; the "fraud signals and recommendation" steps are added to the same job by item 18.
- Test changes made on purpose: the API tests run in inline mode (set in `MockedApiFactory`) so uploads are processed before the response as they always were; the Playwright run uses background mode, so API-driven tests wait for the reading with `waitForDocumentsRead`; the item 2 end-to-end test "fails once, marked Could not be read, retried" became two tests because a transient failure is now retried automatically and invisibly, and a persistent one ends as "Could not be read"; `RecordingTriageQueue` in the WhatsApp queue tests follows the new async interface.
- Review-needed notifications for low-confidence staff uploads are sent only in inline mode; moving them into the pipeline belongs with item 21 (notifications on events).
- Job payloads carry identifiers only; failure text is mapped to a fixed sentence per kind of failure.

## D-025 Item 18 judgement calls
- **Rules decide the advice, the model only explains it.** The recommendation kind and every reason in it are worked out by plain rules from facts already on the claim, so each statement has a source a person can open. A model writes at most a short paragraph in words, and it is dropped if it contains decision or accusation wording (a short list in `AdvisoryLanguage`; to be reviewed by compliance). A real model's output quality is on the real-credentials checklist.
- **Weights and bands are starting values, not calibrated.** Fixed-rule signals weigh 0.10, 0.25 and 0.45 by severity; picture findings 0.05, 0.20 and 0.40; a model note 0.08 (two at most). Bands are under 20, under 45, under 70, 70 and over. They exist so the score is explainable, not because they were tuned on real claims; a human (claims lead and compliance) should review them before a real insurer relies on the bands.
- **The low-documents rule is left out of the score.** The rule engine's own text says low completeness alone is not suspicious; missing documents drive "ask for more" instead.
- **Roles.** The whole box is limited to roles that hold ViewFraudSignals (supervisor, compliance, admin), the same people who see fraud signals today; claims officers do not see it. If front-line staff should see the non-fraud advice ("ask for the police abstract"), that is a product decision for a later change. Responding needs OverrideAiRecommendation.
- **A response belongs to the facts it was given on.** Facts are fingerprinted (reasons, readings, advice); when they change the old response stops showing and is kept only in the saved history and the audit trail.
- **A sixteenth agent, `claim-recommendation`,** was added to the catalogue (so it has a kill switch and appears in the agent runs); the agent count test was changed from 15 to 16 on purpose. It reads through repositories rather than the agent tool registry, like the existing fraud query service.
- The mock summary adds one model concern when a claim's description contains `IIP-MOCK-RISK`, so tests and demos can show a model-noticed reason.
- The score is recomputed on every read from the current facts; only the written explanation and the person's response are stored.
- Fraud rules still look at the most recent 500 claims in the workspace (unchanged); item 35 replaces that window.

## D-026 Item 19 judgement calls
- **Default wording is mine and unreviewed.** The ten default titles and explanations were written for this build, say nothing about cover, amounts or outcomes beyond the status itself, and are shown on the admin page as "to be confirmed by your insurer and legal adviser". A human at the insurer should read all ten, especially Settled, Closed and Waiting for a decision.
- **The timeline needs a link from claim status to stage, and nothing in the platform tracks a claim's stage.** The staff view deliberately does not mark a current stage for that reason. For the customer I made the link explicit data rather than a guess: each product stage can say at which claim status it is reached (`MilestoneStatus`), with built-in defaults for the default stages, so a person can read and change exactly what the customer is told. Waiting on documents and escalation sit where the claim was working, not at the end. If real stage tracking is built later, only `ClaimantTimeline.Build` changes.
- **Not every stage is customer-facing.** The discharge voucher and complaint escalation stages are hidden by default, which gives six customer steps. A product's own added stages are hidden until marked visible with a milestone.
- **No stage editor UI yet.** The three new stage fields can be set through the product API; the product screen does not show them (the stage editor is read only today). Listed as a gap in the summary.
- **Dates on steps are approximate:** the first step shows the received date and the current step shows the last update; finished steps carry no date because the platform does not record when each status was reached (item 20's status change will record it).
- **Kato's status replies** now use the workspace's headline (for example "We are reviewing your claim") after a colon; the "no open claims" sentence was reworded from "is {status}" to ": {status}" so the headline reads naturally. The WhatsApp message to the customer on a status change belongs to item 21.
- The old claimant timeline kept five fixed steps with a "complete" flag; `complete` is kept for older readers and `state` (Done, Current, Upcoming) is added.

## D-027 Item 20 judgement calls
- **Which moves are by hand.** Only moves between Under review, Waiting on documents and Ready for review are open to any claims officer, because they only say where the officer is in their own work. Awaiting approval, Ready for export, Escalated, Settled and Closed are deliberately not choosable: they commit someone else's decision (an approver, an escalation owner, a settlement) and already have actions with their own checks. If the insurer wants an officer to be able to send a claim to approval by hand, that is a policy change to make deliberately.
- **Reopening and de-escalating use the settlement authority** (ApproveSettlementWorkflowStep), the same permission Resolve needs, since undoing a settlement or an escalation is as consequential as making one. Settled claims cannot be reopened at all (money may have moved); Closed ones can, to Under review.
- **The table also documents moves it does not perform.** The workflow rules, assigning, escalating, resolving and the approval step still write status in their own code; the table lists them so the picture is complete and tested for reachability, but it does not yet enforce itself on those paths. Routing every path through one service is part of item 21, where a status change must also trigger the customer message.
- **Entering Waiting on documents by hand does not send the customer a request** (the workflow rule does, once, when it moves a claim there). Whether a manual move should send the same request is decided with the notifications in item 21.
- **Audit wording.** The audit list shows the person's reason as the event summary; the action name `case.status.changed` is on the record. (The existing audit list prefers the reason over the action name; unchanged.)
- The reason is limited to 500 characters; a person's own words are stored as written.

## D-028 Item 21 judgement calls
- **Off by default.** The platform does not start messaging an insurer's customers on its own. An administrator turns status messages on, and separately turns on sending without approval. Both are audited settings changes.
- **The words are the item 19 wording, not a model's.** That makes "admin approved" literal: what is sent is the text the insurer wrote or accepted on the wording page. Free text still goes through the existing customer update flow with its approvals; this item adds no free-text path.
- **Which statuses always need a person** is the existing customer update policy, not a new rule: ready for review, escalation, and anything about a decision (settled, closed). Awaiting approval and ready for export are routine under that policy and may be sent automatically if the workspace allows it; if the insurer would rather those wait for a person, the policy (one function) is where to change it. The default wording for Settled and Closed states an outcome and was written without legal review (D-026).
- **One channel per message, the one the claim came in on,** with SMS then email as the fall-back. Sending the same message on every channel was rejected as noisy and as widening who learns what. A claim with no phone and no email records "NoRecipient" in the audit trail.
- **WhatsApp consent is the recorded consent row, not the chat history.** A customer who has never messaged on WhatsApp has no consent record, so nothing is sent and the update says why. This matches the rule already used for missing-document requests.
- **WhatsApp template parameters** are named: claim_reference and status (the headline). The insurer's template in Meta must use those names. Template approval itself is a Meta process and cannot be proven here (listed in the real-credentials checklist).
- **A mock WhatsApp sender** was added for developer runtimes behind a new `IWhatsAppSenderResolver`; it records into the existing mock outbox. Real sending uses the connected business number. Item 27 makes the resolver per tenant. The resolver exists so the customer update path never reaches into global WhatsApp settings.
- **The hook is best effort.** A status change never fails or rolls back because a message could not be sent; the notifier records the outcome (including "NotSent" with the reason) in the audit trail and the update is kept for a person.
- **The new delivery statuses** ConsentRequired and TemplateRequired are treated as failures by the staff Send button, with a plain explanation, instead of being reported as sent.
- Workflow evaluation, assign, escalate, resolve and approval each call the same hook after saving; the transition table of item 20 still does not enforce itself on those paths.

## D-029 Item 22 judgement calls
- **Permission.** Sending a link is messaging a customer, so it needs SendCustomerUpdate (claims officers, supervisors, admins), not a new permission. Compliance and brokers cannot send one.
- **Consent.** WhatsApp needs a recorded, unwithdrawn consent, as for every other WhatsApp send. A text message or an email is transactional about the customer's own claim, so a missing consent record does not stop it, but a recorded withdrawal always does. If the insurer wants an explicit opt in for text and email too, the check is one function (`ClaimLinkPolicy.ConsentCheck`).
- **WhatsApp outside 24 hours is not sent.** The link message has no Meta template (an approved template would need a link parameter and its own approval), so staff are told to use text or email. Adding a "claim link" template is a later option.
- **The link is never stored in a message the platform keeps.** It is sent from memory and not saved as a customer update, the audit event and the message record for WhatsApp hold a plain sentence, and the mock outbox (developer runtimes only) holds the real message so a test can read it. The real SMS or email providers keep what their own services keep, as for the existing magic link.
- **A link that could not be delivered is switched off at once** (marked used), so no working link exists that nobody holds.
- **The link goes to the contact on the claim,** never to an address typed in, so a staff member cannot send a customer's claim to someone else's number. The token is bound to that contact.
- **Lifetime is 24 hours** like the link the WhatsApp assistant issues (the 15 minute lifetime of the web page request is for a link used at once).

## D-030 Item 23 judgement calls
- **Pieces are held in the database, not blob storage.** The storage port has no "write by key" or delete, and adding one would touch every storage adapter; a quarter-megabyte piece per row for at most a day is fine for the volumes here, and pieces are deleted when the file is finished, cancelled or expired. If volumes grow, moving pieces to blob storage is a swap behind `IUploadPartStore`. Item 34 (retention) should also sweep sessions that were abandoned after the day is up; today an expired session's pieces are removed the next time the same claim starts any upload.
- **Sequential pieces, one at a time.** Parallel pieces would be faster on a good connection and worse on a bad one (they compete for the same narrow pipe and each retries separately). The point of the item is poor connections.
- **Resume is by the browser's own identity for the file** (name, size, last modified, slot). A browser cannot silently reopen a file after a reload, so the customer must choose the same file again; the page remembers and says so. A file copied or edited in between is a different file and starts clean.
- **Whole-file fingerprint.** The phone computes a SHA-256 of the file and the server compares it to what it assembled; a mismatch discards the pieces and the page starts the file again once. It needs the whole file in memory, which is fine up to the 25 MB limit.
- **Evidence is never shrunk.** The size target applies only to pictures of paperwork. Large evidence photos rely on pieces. The 450 KB target is a starting value, not tuned on real documents.
- **A 410 or 409 restarts the file once, automatically.** Beyond that the customer sees the message and can choose the file again.
- **Test speed.** Retry waits are scaled by an environment variable (`NEXT_PUBLIC_UPLOAD_BACKOFF_SCALE`) which only the test run sets; real use is unscaled.
- The portal's staff upload path and WhatsApp/email attachment paths are unchanged: pieces are for the customer's browser.

## D-031 Item 24 judgement calls
- **No PDF library.** The summary is written by a small writer in the code base (`SimplePdfDocument`) using the standard Helvetica fonts, so nothing is embedded and no licence is added. It writes plain Latin text only (accents are folded to the base letter, other scripts show as question marks); a summary in a language that needs other scripts would need a real PDF library with an embedded font. It was checked in two independent readers (pypdf and PyMuPDF) but not in Acrobat or a print preview.
- **Names.** Documents and evidence are renamed after what they are (`PoliceAbstract_CLM-....pdf`, `PhotosOfTheDamage_CLM-....jpg`); the manifest keeps the original name beside the new one. The bytes in `02_Evidence` are the originals; the pictures of one paperwork slot are the single PDF built from them (item 12).
- **Who can export.** The same permission as the existing evidence export (supervisors, compliance, administrators), which also hold the permission to see fraud signals, so including the review score does not widen who sees it. A claims officer cannot download a pack.
- **Memory.** A pack is assembled in memory: up to the claim's files (25 MB each) plus the summary. Fine for a claim; very large claims would want streaming, which is a later change.
- **The timeline in the summary is the audit trail** (the last 80 events, in order, with who did it), not the customer's timeline.
- **The JSON audit pack is kept** as asked; the two exports are separate.
- **The builder is a service (`IClaimsPackBuilder`)** so item 25 can email the same pack without a second implementation.

## D-032 Item 25 judgement calls
- **Attachments did not exist; I added them.** No email sender could carry a file or even set a subject (every email was "Insurance claim update"). Adding both was needed for the item, so `CommunicationSendRequest` gained optional `Subject` and `Attachments` (every existing send is unchanged), and the mock, SMTP and Graph senders carry them. The mock path is proven by tests; SMTP and Graph attachment sending cannot be proven without real mail credentials and is on the real-credentials checklist (Graph files over 3 MB would need an upload session, which is why the attachment limit is 3 MB).
- **Larger than 3 MB goes as a link, smaller is attached.** A zip of customer documents is personal information; a link can expire, be counted and be audited, an attachment cannot be taken back. If an insurer would rather never attach, the limit is one constant.
- **The link is a long random token, kept only as a fingerprint, valid 7 days and 10 downloads, opened on a page that downloads only on a press.** Anyone holding it can download, by design (the recipients are outside the platform). Rate limiting of the public endpoint belongs to the deployment's front door and is not built here. Links cannot yet be withdrawn early (they run out or expire); a "revoke" button is a gap listed in the summary.
- **The pack is stored for the link through the existing evidence pack storage** (the one the JSON audit pack export already uses), so it follows that provider's retention; item 34 should cover expired packs.
- **Triggers.** "Complete" sends once per claim when the claim is at 100 percent (checked after uploads and after each document is read); a claim that drops below and returns to 100 does not send again. "Status" sends when a claim reaches the chosen status. Both queue a durable job; a claim moved to the status twice sends once. Replaced documents never resend.
- **Who receives it is the insurer's list, not the customer.** The recipients are business contacts the administrator names; no customer consent is needed because the customer is not contacted, but the email says it contains personal information and to keep it secure. Whether the insurer's data processing terms allow those recipients is for the insurer (to be confirmed by legal).
- **Runs as the platform.** Automatic sends are recorded as `system:claims-pack`; a manual send is recorded as the person who pressed it.
- Sending from the status path is funnelled through the existing customer-message hook (`ClaimStatusNotifier`), so every route that changes a status can trigger a pack without a second hook in each endpoint.

## D-033 Item 26 judgement calls
- **Offered, never silent.** Remembered details are shown to the customer to tick and apply, and a document is copied only when they press "Use the one on file". Even in the new-claim form, where prefilling is the whole point, a line says what was filled in and from which claim, and the customer submits the form themselves.
- **Same customer means the same policy number, phone number or email, within one workspace.** There is no customer master record that links claims reliably (several people can share a phone). The risk of a wrong match is that someone sees a detail from another household member's claim; the defence is that offers are shown only to a verified claimant for their own claim, and only the short list the insurer chose. If an insurer's customers often share phones, switch memory off or narrow the list.
- **Default lists are cautious.** Details: driving permit number, preferred contact method and vehicle registration (about the person or vehicle, not about what happened). Documents: ID only. Everything else is the administrator's choice by key. Evidence is never offered by default.
- **A reused document is a copy, not a link to the old file.** Retention or deletion of one claim's files (item 34) must not break another claim's, and the new copy is read afresh in the new claim's context. The cost is storing the bytes twice.
- **WhatsApp does not do the reuse itself.** Papers are never handled in the chat (they carry personal details), so Kato names what is on file and sends the customer to the secure page, where the same one-press reuse is. This keeps one reuse path with one set of checks.
- **Reads scan the workspace's claims** to find earlier ones; item 35 replaces that with an indexed lookup. It also reads only claims in the caller's own workspace.
- **Default on, with a switch.** Remembering across claims is a further use of what the customer already gave for a claim; it is shown only to them, but whether it fits the insurer's privacy notice is for the insurer and legal (to be confirmed by legal), hence the admin switch and the note beside it.
- **Staff can see** on a reused file which claim it came from (`reusedFromClaim`); there is no staff screen yet for what a customer's memory holds, which is a gap listed in the summary.

## D-034 Item 27 judgement calls
- **Routing is by business phone number, proved by that workspace's own app secret.** Meta signs with the app secret, and each insurer here brings its own app, so the secret that verifies a webhook is looked up from the number the webhook names. A number nobody connected is answered exactly like a bad signature (401), so a stranger cannot learn which numbers are connected. A webhook naming two workspaces' numbers must verify for both, which one signature cannot, so it is refused whole. If Meta's app were shared by all insurers (embedded signup), this would change to one platform secret plus routing by number.
- **A number belongs to one workspace.** Enforced at save (409) and again at routing (a number held by two rows resolves to nobody rather than guessing).
- **A cross-workspace read exists on purpose** (`ListActiveAsync`), only to build the routing snapshot and to check the one-number rule. It returns decrypted credentials only inside the singleton snapshot, never to a caller or browser. The snapshot refreshes on save, after 30 seconds, and on an unknown number (at most every 5 seconds). With several instances a freshly saved number may take up to that long to route on another instance. If the store cannot be read the earlier snapshot stays in force.
- **`Current` is only the sole connection.** With more than one connection it is null; every per-workspace caller uses `ForScope`. The old single-connection signature and download overloads remain for a one-number deployment and are not used by any webhook path.
- **The in-memory assistant queue is gone (carry-over of D-024).** Replaced by a saved job in the workspace's own scope. The job holds message identifiers; the words are read back from the message store. Tests of the old queue were rewritten as job tests with the same behaviours (answers after the request, hands an opened claim to review, a failing batch does not stop the next, a batch past its time goes to a person with a fresh token). The "queue full" test was dropped on purpose: a database queue has no bound. If the job cannot be saved the webhook still handles the batch itself, so a message is never dropped. Retries are capped at three because a retry after a reply was sent could say it twice; the assistant already hands a failed message to a person itself.
- **Per-workspace Kato uses an async-local binding, not a rewrite of every reply.** The fixed replies read `KatoBrand.Current`; binding the workspace's brand for the duration of the work makes all of them speak for the right organisation without threading a brand through hundreds of call sites. The binding is made in the entry points that handle one workspace's work (assistant, escalation, outreach, triage, insights). A code path that reads `KatoBrand.Current` outside those would see the deployment default, which is a risk to remember when adding entry points.
- **The covers are the workspace's products, with an offer.** The offer (insurer, summary, who it is for, waiting period, papers, price levels, the name the customer hears) is part of the product version, so changing what Kato says about a cover goes through the same history and second-person approval as changing the cover. The built-in catalogue is now seed data for the demonstration workspace, written onto its products. There is no screen to edit an offer yet (API only); listed in the summary.
- **Unconfigured means nothing for sale, except in developer and demonstration runtimes.** A real insurer's customer is never offered another insurer's covers. The default organisation name for a workspace that set none is still the deployment default (Nile Shield unless configured), so each real workspace must set its own.
- **Caption names the slot, otherwise the reader decides.** The caption must match exactly one single-file slot that is still empty (every meaningful word, in the slot's name); slots that take several pages or photos are left to the recogniser because their page order matters. A wrong guess would file a paper in the wrong place on a claim; no guess only costs a look.
- Not proved without credentials: real Meta signatures with real app secrets, template and 24-hour-window behaviour, and delivery receipts. The mock cannot send WhatsApp, so the end-to-end tests cover settings, isolation and refusals rather than a live conversation.

## D-035 Item 28 judgement calls
- **Library: MailKit 4.18.1 (MIT).** The platform had no IMAP client and writing one would be riskier than a maintained library. 4.8.0 carried a known vulnerability advisory (NU1902, which would break the zero-warning build), so the newest release is used. Its dependency MimeKit is also MIT-compatible (MIT).
- **Always TLS, no plaintext option.** Port 993 is wrapped from the first byte; any other port must offer STARTTLS or the connection is refused. Certificates are validated normally. There is deliberately no "allow insecure" switch.
- **Public hosts only (SSRF defence).** The host is typed by an insurer's administrator, so it could otherwise be used to probe the platform's own network (database, cloud metadata address, other tenants' services). A host must resolve entirely to public internet addresses and the connection is made to the address that was checked (so a name that changes its answer between check and connection gains nothing). Developer and demonstration runtimes may also reach private addresses so a local test mail server can be used. This is checked when the mailbox is saved and again on every connection.
- **The password is a secret like any other connection secret**: encrypted with the same protector as the other tenant connections, decrypted only for the moment of a call, never returned (the API says only that one is saved) and never logged. Provider error text is not shown; only a fixed plain sentence is.
- **Basic IMAP login only.** Hosts that have switched off passwords for IMAP (Gmail and personal Outlook accounts require OAuth or an app password) work only with an app password. IMAP OAuth is not built. Microsoft 365 uses the Graph route instead, which does not use passwords.
- **Microsoft 365 per insurer.** The platform keeps one app registration; each insurer consents to it in its own Microsoft Entra directory and names that directory on the mailbox, and mail is read through it. A mailbox with no directory uses the deployment's own (the earlier behaviour). Tokens are requested per call, not cached; fine at five-minute polling, a cache belongs with item 35.
- **The scheduled pass reads one cross-workspace list of scopes** (never mailbox details) and then works one workspace at a time inside its own scope. Failures are isolated per mailbox and per workspace.
- **Collection is by "unread".** A message stays unread at the host until a person turns it into a claim, so it is re-listed each pass (at most 10 at a time, newest first) and skipped by its stable id. This is the same behaviour as the Microsoft route. A mailbox with more than 10 unread messages shows only the newest 10 until some are processed; that limit is a deployment setting.
- **Ingestion still stops at the inbox.** Turning an email into a claim stays a person's decision with a recorded reason, as before.
- **Attachments are slotted by file name only when that is exact.** The file name must name exactly one empty single-file slot; otherwise the document reader decides, and a person looks if it is not sure. Same rule and same matcher as WhatsApp captions (D-034).
- **A mailbox that stops working is visible** (last check time and "Could not connect") instead of looking like an empty inbox. The note is written only when the answer changes or after 30 minutes, so a healthy mailbox does not cost a write every pass.
- **Not provable here**: the MailKit calls (connect, list unread, fetch an attachment, mark read, move) were not run against a real IMAP server, because none is available. The rules around them (host policy, source routing, stable ids, isolation, passwords, refusals) are tested; the wire behaviour is on the real-credentials checklist.
- **Not built**: deleting a mailbox from the screen, IMAP IDLE (push), IMAP OAuth, attachments larger than 25 MB (refused with a plain reason).

## D-036 Item 29 judgement calls
- **The customer's link carries the insurer's link name; an insurer's own verified web address is the alternative.** There is one shared customer portal for the deployment, so the page cannot know whose it is from a build-time setting. A short name in the link (`t=`), kept for the visit and sent as a header, is the simplest thing that works on one origin. The name is not secret and grants nothing: every claimant route past link issuance still needs a verified claimant session, and issuing a link never says whether a claim exists.
- **Browsers cannot choose an insurer on a shared deployment.** Outside Development the old behaviour on an unpinned deployment was to trust the `X-Tenant-Id` the browser sent. It now refuses unless a known link name or verified address names the workspace. A header that disagrees with the link name is refused. A deployment pinned to one insurer still refuses another insurer's link.
- **A name two workspaces hold belongs to neither.** Link names, web addresses and SMS secrets are checked unique when saved, and again when read (two administrators saving the same name at once resolve to nobody rather than to one of them). There is no database unique index; the checked save plus the fail-closed read is the control, and an index would be a sensible addition at item 35.
- **A web address is proved before it is used.** Otherwise a workspace could claim a company's real address and, once that company pointed its name at the platform, receive its customers and have the browser allowance for its origin. The proof is a text the platform issues and the insurer publishes at `/.well-known/iip-portal-verification` on that address. The check is made only to public internet addresses (same rule as IMAP hosts) over TLS with certificates validated, without following redirects, reading a few hundred bytes. It proves control of the address, not that DNS or a certificate is set up for the platform; routing the address to the portal remains a manual step for whoever runs the deployment (listed in the real-credentials checklist). The proof is not repeated, so an address the insurer later loses control of stays verified until it is changed or removed.
- **CORS now consults the directory.** A browser page on an insurer's verified `https://` address on the default port is allowed to call the service with credentials, in addition to the configured portal origins. Unverified or unknown origins are not.
- **The SMS callback is a per-insurer secret path, not a signature.** The gateway (EgoSMS) calls a URL we give it; the secret in the path is the only authentication it supports. Only a SHA-256 of the secret is stored, so it is shown once and cannot be recovered, and rotating it stops the old one immediately. A report can only update messages in the workspace that owns the secret. The deployment-wide secret still works for a deployment dedicated to one insurer.
- **Branding is limited to what cannot harm a customer.** A name, an https logo address (shown as an image with no referrer), a button colour that passes a contrast check against white text (4.5 to 1), a phone and an email. No free HTML or CSS. The page falls back to the platform's own look when a workspace has set nothing or the branding cannot be loaded.
- **Public branding is public by design**: `GET /api/v1/client-portal/branding` returns only the six display fields and nothing from the admin record (no hash, no challenge, no hostname state).
- **A race from item 26 was found and fixed on the way.** The full end-to-end run once showed a reused document without its "reused from claim" mark: the mark was written in a second save after the file was stored, and the background reading of the file saves its own copy of the document, which could overwrite it. The mark is now set when the copy is first saved (`StoreUploadedFilesAsync` takes the claim it came from), so there is no second save to lose.
- **Not built**: a screen to remove the portal identity or the web address, automatic DNS or certificate setup for custom addresses, and per-insurer sign-in pages beyond the branded header. Staff sign-in is unchanged (item 30).

## D-037 Item 30 judgement calls
- **Two kinds of sign-in, one way of deciding what a person may do.** Entra tokens and the platform's own tokens are both accepted; the API picks the checker by the token's issuer. Neither token carries authority: tenant, workspace and role are read from the membership store keyed by user id on every request, exactly as for Entra users. A platform token also carries a role and workspace claim, used only as the starting value for the screen; the server re-reads membership.
- **Platform tokens: HS256, 8 hours, no refresh, no revocation.** The signing key is a deployment secret (`INSURANCEINTELLIGENCE_LOCAL_AUTH_SIGNING_KEY`, base64, at least 32 bytes; random per start in a developer runtime so developer tokens die with the process). A deployed environment without a key reports "Not configured" for email and password sign-in rather than inventing one. Changing a password does not end tokens already issued (they last at most 8 hours); a token deny-list or a short token plus refresh belongs with item 34 or a later hardening pass.
- **Passwords.** PBKDF2-SHA256 with 600,000 iterations and a per-person salt (the OWASP figure for this algorithm; no new package). Policy: 12 or more characters, not on a short list of very common passwords, not containing the email name or the company name. No composition rules (they push people to predictable patterns). Not built: checking passwords against known-breach lists (needs a service), multi-factor sign-in (Entra covers companies that want it).
- **Same answer for every failure.** Unknown email, wrong password and a paused account return the same 401 and the same words, and run the password check anyway so timing does not tell them apart. Five failures pause the account for 15 minutes (the pause is per account, so a stranger can pause someone's account for a short time; chosen over the alternative of no limit; the sign-in endpoint is also rate limited per address).
- **Email links are secrets and are treated as such.** Sign-up, reset and invitation links carry a random 256-bit value. Only its SHA-256 is stored (and row keys derive from that), so a read of the database gives no working link. Links work once and expire (sign-up 24 hours, reset 1 hour, invitation 7 days). Forgot-password always answers the same whether or not the email has an account.
- **Sign-up creates nothing until the email is proved.** The pending request holds the details and a password fingerprint; the workspace, user and membership are created on confirmation. Confirming twice, or after expiry, is refused. A hidden field only software fills in quietly drops bot submissions with the normal "check your email" answer. There is no captcha (a third-party service); the rate limit and the proof of email are the controls, and a captcha is a sensible addition if abuse appears.
- **Starter content is deliberately small.** On confirmation: tenant `tenant-<random>`, workspace `workspace-claims`, an Administrator, operating settings naming the company (used by the WhatsApp assistant), a customer-portal link name made from the company name, and three Draft products (Motor, Medical, Property) with the standard document lists, created through the normal product service. Drafts need a person to review and publish, so nothing is offered to customers until a human says so. No sample claims, customers or numbers are created.
- **Invitations use the normal seat limit and one open invitation per email.** A new invitation replaces the previous open one. An email that already has a platform sign-in accepts by proving its password; a new person chooses a name and password. A person who is already a member is refused with a plain sentence. Invitations are for platform sign-in. Pre-approving a Microsoft account by email (so an invited Entra user is added on first sign-in) is not built.
- **Where emails come from.** The platform's own sender (the deployment's email provider) for sign-up and reset, because the workspace does not exist yet; the workspace's own sender for invitations once it has one. In the mock runtime they land in the mock outbox, sign-up and reset under the scope `iip-platform` / `identity`.
- **Sign-up is on by default only in developer runtimes.** A deployed environment must opt in (`INSURANCEINTELLIGENCE_SELF_SERVE_SIGNUP=true`); otherwise the page says it is not open. The rate limit counts by connection address, so behind a proxy the deployment must forward the real address (`ASPNETCORE_FORWARDEDHEADERS_ENABLED=true`) or everyone shares one allowance.
- **The terms page is draft wording** in plain language and says so on the page. It must be replaced or approved by legal before real companies rely on it.
- **A developer's headers stop working once someone signs in.** In a developer runtime the convenience headers are used only when no token is present; a signed-in tab sends its token, and the server treats it as a real identity (deployed semantics for permissions), so what a developer sees after signing in is what a customer would see.

## D-038 Item 31 judgement calls
- **One place counts, not every feature.** The three model interfaces (single prompt, tool calling, embeddings) are wrapped once at start-up, so every present and future caller is counted and no feature can forget. Customer-update drafting and the policy assistant call a model by their own route: the first records directly, the second already wrote its tokens to its own action row, which the totals include. A new model route must either go through one of the three interfaces or record itself.
- **Recorded in the action log, as the plan says, but kept out of every list.** A bare "ModelCall" row (no prompt, no answer, no person) per call sits beside real actions. The two action lists (workspace, per claim) exclude them in the query, so no screen, report, compliance view or agent tool shows them. Totals read dedicated columns (month, tokens, cost in millionths of a dollar) with an index, so a month's usage is a few indexed sums, not a scan of JSON.
- **Counts are the provider's own.** Tokens come from the provider's reported usage. A call whose provider reports none is still counted as a call and counted as "unpriced"; nothing is estimated from text length for a real model. The mock reports a rough figure (characters / 4) so local runs have numbers.
- **Prices are configuration, not code.** `INSURANCEINTELLIGENCE_AI_PRICING` is JSON keyed by the model deployment name (or a model-version prefix; the longest match wins). A model with no entry has no cost: the card says so, and the cost meter turns on only when something could be priced. The mock is free. The old class that assumed gpt-4o 2024 prices is deleted; the two endpoints that used it now ask the configured model.
- **Cost is rounded to millionths of a dollar and shown in cents on the page** (the meter has whole-number fields). Many small calls sum exactly; only the final display rounds.
- **Month, not rolling.** Usage is the calendar month in UTC, the unit item 32 will bill and limit by. Rows from before this change have no month and are not counted (a one-off backfill is not worth a job on a fresh platform; a deployment with history can run a short script if it wants it). Documents stored before this change report no size until they are next saved, so storage understates old files in a long-running deployment.
- **Storage counts everything held**, including superseded and removed-by-customer files, because nothing is deleted yet (retention is item 34). It is counted from stored sizes, not from the blob account.
- **Counting never fails the work.** A recording fault is caught and logged by type; the model result is returned unchanged. The cost is occasional undercounting, which the log makes visible.
- **Attribution**: a chat call is billed to the tenant and workspace named on the request, or the request's own tenant; a tool-calling or embedding call is billed to the ambient request or job tenant and is skipped (not misfiled) when there is none. The WhatsApp assistant job sets its own tenant, so its steps are counted.
- **Not built**: Document Intelligence page counts as their own meter (documents are counted instead), per-agent or per-user breakdowns, a usage export, and alerting at a threshold (item 32 adds allowances and upgrade prompts).

## D-039 Item 32 judgement calls
- **List prices and allowances are placeholders for the business to confirm.** Free, Agent about US$ 20 (UGX 75,000), Team about US$ 99 (UGX 370,000) and Enterprise by agreement, with the allowances in `Domain/Billing/Plans.cs`. They can be replaced with `INSURANCEINTELLIGENCE_PLAN_CATALOGUE` (JSON) without a release; a malformed value, a duplicate key or a catalogue with no free plan falls back to the defaults so a typo cannot leave workspaces with nothing to be on. A receipt is a payment receipt, not a tax invoice: VAT and invoicing rules are not handled and need finance and legal advice.
- **Existing workspaces are grandfathered.** A workspace with no subscription is on "Standard" and keeps the seat and claim limits in its own operating settings, with no enforcement beyond today's. Only companies that sign up for themselves, or buy a plan, are held to a plan. Otherwise every demo and pilot workspace would be limited overnight.
- **A plan's limit is a ceiling the workspace's own setting can lower but never raise.** Otherwise an administrator could lift their own plan's limit in the operating settings. A plan that sets no limit (Standard, Enterprise) defers to the setting.
- **Allowances are by calendar month (UTC), matching the usage meters.** A claim is counted in the month it was opened, from a month key kept beside it; claims opened before this change have no key and are not counted.
- **What is enforced, and what is only shown.** Claims are refused at creation (staff, the portal's staff tools, and the WhatsApp assistant); AI use is refused before a model is called (single-prompt and tool-calling models; embeddings are not blocked because indexing runs in the background); seats come from the plan. Documents and storage only warn: a customer sending papers for an open claim must never be turned away for the insurer's plan. The check reads the current count and does not lock, so concurrent requests at the limit can overshoot by a few; that was judged better than blocking every claim behind a lock.
- **Customers never hear about plans.** When the assistant cannot open a claim because of the allowance, the customer is told a person will contact them and nothing is promised; the model is told not to give a claim number or a reason. Staff get a 402 with the plan name, the limit and the next plan up.
- **Payment attempts follow one rule: a callback is only a nudge.** The callback address carries an unguessable secret (only its fingerprint is stored, compared in constant time) and its body is never read. The platform then asks the provider what became of the payment and settles only from that answer, and only if the amount and currency it reports equal what was asked. A wrong amount is not accepted and is audited for a person to look at. This works the same for all three providers whether or not they sign their callbacks.
- **A payment is settled once.** Settling is idempotent (a settled attempt is never settled again, so repeated callbacks cannot issue two receipts or extend twice), a second press of the pay button within 15 minutes returns the same attempt rather than asking the phone again, and a failed attempt leaves its invoice open so the next try reuses it.
- **The payer's phone number is kept only while the attempt is pending.** It is blanked when the attempt is settled. No card detail is ever collected: the card gateway's own page takes it.
- **Reconciliation.** Every two minutes the platform asks about attempts still waiting after three minutes; one that has waited 24 hours with no answer is closed as expired so it cannot be paid late by accident. The timer runs inside the API (and is switched off with `INSURANCEINTELLIGENCE_BILLING_WORKER=Off`); several API instances would each run it, which is safe because every pass is idempotent.
- **No automatic monthly charge.** Mobile money cannot be charged on its own, so each month is a payment the administrator makes. About five days before a paid month ends an invoice is issued and the administrator emailed; if unpaid at the end the plan goes "payment overdue" but still applies for seven days; after that the workspace is held to the Free limits ("lapsed"). Nothing is deleted at any point and paying restores the plan. A renewal paid early extends from the end of the current period, not from today. Switching between paid plans takes effect when paid, with no pro-rating. There are no refunds in the product (a refund is a finance action at the operator).
- **Live payment adapters are written to each operator's published collection API and have not been run against a real account** (no credentials exist for this build). They are tested against a stand-in for each operator for request shape and status mapping only. MTN's sandbox only supports one currency and Airtel's token and status shapes may differ by market, so each needs a first run with real test credentials (listed in the real-credentials checklist). An adapter without its credentials reports itself not configured and its method is not offered.
- **Payments default to Disabled.** There is no fake success path: with no provider set up the page says "Not configured". The pretend operator is registered only in developer and demonstration runtimes (the same rule as every other Mock provider).
- **The enrolment payment for IIP Academy (item 33) uses the same payment service**; only the "what happens when it is paid" handler differs.
- **A flaky test from item 27 was fixed at its cause.** `TwoWorkspacesServedAtTheSameTimeEachHearTheirOwnOrganisation` failed about one run in twelve, and every run under load, because its stand-in stores were plain lists written by 24 tasks at once, so one message sometimes hit the assistant's failure path. The stand-ins now use a lock-protected list (`Support/SafeList.cs`). No assertion was changed or weakened; the product code was not at fault (each real store serialises its own writes).

## D-040 Item 33 judgement calls
- **Learners are not users of any workspace.** A learner has no tenant, role or permission in the staff app; they hold an Academy session that can reach only the `/api/v1/learn` routes and only their own records. Their records live in one fixed platform scope (`iip-academy/learners`). What an insurer owns (its access codes, and the written work of learners it sponsored) lives in the insurer's own scope and is listed only by that scope; the learner's account, email and progress are never visible to an insurer. A sponsor sees a learner's name only on a code they used and on work sent for marking.
- **Sign-in by emailed link, no password.** The link carries a random 256-bit secret kept only as a fingerprint, works once, and expires in an hour. A session is a random token (fingerprint stored) valid 14 days, sent in a header (`X-Academy-Session`), not a cookie, so it is not sent by other sites. The browser keeps it in local storage; a script injected into the page could read it, which is the cost of not using cookies and is acceptable for training records. Asking for a link answers the same whether or not the email is known, and sending is rate limited per address of the caller (not per email, so someone could send many links to one inbox; a per-email limit is a sensible later addition).
- **Courses are authored once.** The content stays in the portal's `courses.ts`; an exporter writes the JSON the API serves and marks against, and a check in `pnpm test` fails if they differ. The API serves content only to an enrolled learner; the check answers are in the same file but are never put in a response (a test asserts the words "answer" and "why" are absent from course and catalogue responses until a question is answered correctly).
- **Marking.** The check questions are objective, so the server marks them; passing needs every question right, as the staff version always did, and a learner may retry without limit (attempts and best score are kept). Written work is staff-marked: it goes to the sponsoring insurer, or to the workspace named in `INSURANCEINTELLIGENCE_ACADEMY_OPERATOR_WORKSPACE` ("tenant/workspace") for learners nobody sponsored; with neither, written work cannot be sent and the exercise is self-practice, said plainly. **A certificate does not wait for marking**, because a learner whose sponsor never marks must not be stuck; marking is feedback. If a sponsor should be able to require it, that is a setting to add. Only people with the administrator permission can mark (no separate "tutor" role was added).
- **Access codes.** 12 characters from a 32-letter alphabet (about 60 bits), shown once and stored only as a fingerprint with the last four characters for recognition. Single use, optional expiry, can be withdrawn while unused. Redeeming is serialised in a process lock so a code cannot be used twice at once on one server; two API instances could in theory both accept the same code in the same instant (a database uniqueness rule on redemption is the real fix and belongs with item 35). Wrong codes give one answer whatever the reason, and five failures pause that learner's code entry for 15 minutes.
- **Payment.** A learner pays through the same service and providers as plan billing (mobile money, card), in UGX or USD, one payment per course, priced by defaults of US$ 50 or UGX 185,000 that `INSURANCEINTELLIGENCE_ACADEMY_PRICES` overrides per course and currency. A price of zero enrols at once. Enrolment becomes active only from the provider's confirmed answer (the same rule as plan payments), and the learner is emailed. The staff Academy's old per-workspace price setting is left alone; it is not used by the public pages. There is no refund path in the product and no VAT or receipt number for course payments (the enrolment email is the receipt); finance and legal need to decide both.
- **Certificates.** Numbered `IIPA-XXXXX-XXXXX` (about 50 bits, unguessable), issued once with the name the learner chose at that moment, which cannot be changed afterwards. The public check shows name, course and date only, never an email, and is rate limited. Certificates are not revoked by anything built so far (a withdrawn-certificate list is not built). The wording stays "certificate of completion, not an accredited qualification".
- **Video.** `INSURANCEINTELLIGENCE_ACADEMY_VIDEOS` maps `course/module` to an https address and a title; anything that is not https or names no real module is dropped. A direct .mp4 or .webm plays on the page; any other address is a link that opens in a new tab (no third-party player is embedded, so no third party sees the learner). No video is supplied: the content to record is outside this build.
- **Not built**: erasure and retention of learner records (item 34 covers them with everything else), certificate revocation, per-learner reporting for sponsors, per-email limits on sign-in links, and a "tutor" permission separate from the administrator.

## D-041 Item 34 judgement calls
- **Nothing is deleted by default.** A retention period is an explicit choice (0 or no entry keeps the record), because an insurer's obligations differ by country and product and a wrong default would destroy records it must keep. The periods and what they cover are for the insurer's legal and compliance staff to set; the platform suggests none. A closed or settled claim is the only thing a claim period deletes; an open claim never expires.
- **Erasure keeps the claim, not the person.** An insurer must keep a record of the claims it handled (for audit, reinsurance and financial reporting), so an erasure removes what identifies the person (name, phone, email, what they wrote, their answers, their documents and stored files, chats, consents, portal links, profile) and keeps the claim's id, reference, status, dates, amounts and policy number. The policy number is kept because it is the insurer's own contract reference, which also means a person whose policy number is on an erased claim could still be identified by the insurer through its policy records, which erasure does not touch. Whether that satisfies a particular regulator (Uganda's Data Protection and Privacy Act, others) is for legal advice, not for this build. The audit trail is not erased: its entries describe actions and reasons, not customer content.
- **A legal hold beats everything.** A held claim is skipped by retention and by erasure; the evidence names the claim references that were left alone, so nobody believes a held person was erased. Placing and releasing a hold need the administrator permission and are audited. Holds are per claim; there is no whole-workspace hold or per-person hold (erasing by phone skips each held claim it finds, but chats and consents keyed to the number are still deleted, which is a gap if a hold is meant to protect conversations too).
- **Files first, then records.** A claim's stored files are deleted before its rows, so a failure leaves the rows as the list of what remains and repeating the request finishes the job. A claim whose files could not be deleted is not anonymised and is named under "to retry" in the evidence. The retention timer repeats the pass every six hours, so a transient failure heals by itself.
- **Finding a person's other data is by looking for their number or email in what is stored.** Chats, consents, portal links, profiles, leads and emails are stored as documents with no phone or email column, so erasure compares by the last nine digits of the phone (however it was written) and the email as written, inside the one workspace. This can delete a record that merely mentions the number (for example an officer's note quoting it), which is the safer way to be wrong; the preview shows the counts first. The contacts on the person's claims are added to the search, so asking by policy number also finds their chats. It is a scan of that one workspace's rows, so it is not meant to be run constantly (item 35 covers the scans that run constantly).
- **The evidence is deliberately thin.** A deletion record keeps the time, the actor or rule, the reason, a 16-character fingerprint of who was asked about (not reversible to the phone or email) and counts by kind. It is kept after the data is gone and is itself never deleted by the platform. Retention passes that delete nothing write no record (the audit trail would otherwise fill with empty entries).
- **What erasure does not reach.** Things outside this platform's own database and file store: the WhatsApp or email provider's copy of a message, a bank's or reinsurer's copy of a claims pack sent to them, backups, and soft-deleted files inside the storage account. Backups: Azure SQL point-in-time backups keep deleted rows for 7 days (35 in production) and expire by themselves. Soft delete: a deleted file can be recovered from the storage account for `blobSoftDeleteDays` (now 7 days; it was tied to the 365-day document retention, so erased files would have stayed recoverable for a year). A data-subject erasure is complete only when those windows have passed. Claims packs the platform itself stored (for a link or an email) are deleted when their claim is. The database change-tracking of Azure itself is outside the product.
- **The older conversation retention is left in place.** A Phase 6 policy (`RetentionPolicy`, days, default 365, manual endpoint) already deletes old WhatsApp conversation turns. It is untouched. The new "WhatsApp conversations" period covers the same turns and also the message log, so with both set the shorter period wins in practice. They should be merged into the one setting by a human who knows which deployments rely on the old default; it was not done silently here.
- **Encryption.** Azure Storage and Azure SQL encrypt at rest by default with Microsoft-managed keys; the templates now say so explicitly (storage services on, SQL transparent data encryption on) so a later edit cannot quietly switch it off. A customer-managed key is optional: give the vault address, key name and a user-assigned identity, and storage (latest key version, automatic) and SQL (a named key version, with automatic rotation on) use it. **One step is manual and cannot be done in the template**: the identity must be given the "Key Vault Crypto Service Encryption User" role on the vault, and the vault must have soft delete and purge protection on, before the deployment. Double encryption (`storageInfrastructureEncryption`) can only be chosen when the account is first created. The templates compile with `az bicep build`; they were not deployed, so the first deployment with a customer key is on the real-credentials checklist.
- **Not built**: erasure of a learner's Academy records (their data is in a separate scope with its own email-keyed account; a learner erasure endpoint belongs with the next privacy pass), a whole-workspace erasure on closing an account, deletion of the audit trail, export of a person's data (a subject access request), and evidence export as a file.

## D-042 Item 35 judgement calls
- **Indexes find candidates; the old rule still decides.** Each lookup column is a deliberately coarse form (policy number in upper case, the last seven digits of a phone number, the email in lower case), so an indexed lookup returns every record the old exact rule could have matched and sometimes a few more. Every caller keeps its own exact rule (the phone-number matcher, the contact matcher, the same-customer rule), so no behaviour changed. The last seven digits were chosen because two numbers the platform treats as equal (with or without the country code or the leading zero) always agree there.
- **Older rows are not trusted to have columns.** A row saved before the columns existed has a lookup version of 0. Every lookup also reads those rows and filters them in memory, so an upgrade never makes a claim disappear while the backfill runs. The backfill runs once, 20 seconds after start-up, in batches of 200, and is safe to repeat or to run on several instances at once (it only fills fields that are derived from the row itself). When it has finished, the extra read finds nothing and costs one indexed lookup on the version column.
- **Stores that cannot index still work.** The new repository methods have default implementations that read the workspace and filter. Any test double or future store therefore stays correct without being rewritten; only the Entity Framework store is fast.
- **Email matching by policy number now looks up words, not substrings.** The old rule read every claim and asked "does this email contain this claim's policy number?". It now takes the words in the subject and body that look like a policy number (letters, digits, dashes and slashes, 4 to 41 characters, at most 40 words) and looks those up, then confirms with the same contains test. A policy number written with spaces inside it is no longer found in free text; one written as a single token (the usual way) is. The sender's identity is still decided only from the From address.
- **What was not changed, and still reads a whole workspace.** Dashboards and reports that count or group everything (the command centre, executive and compliance summaries, reports, the brief, my work, global search, the claim type counts, the retention watch) need every claim to answer their question, and a workspace-wide search is a different problem (text search). They are the next thing to move to a database query or a search index when a workspace reaches tens of thousands of claims. The retention pass and the data-subject erasure also read a workspace's chats and messages to look for a number, which is acceptable for a daily job and a rare request.
- **No database uniqueness rule was added for link names or hostnames or code redemption** (items 29 and 33 noted this). Those need a unique index on a column that does not exist yet and a decision about what to do with existing duplicates, which is a data migration for someone who can see the real data.

## D-043 Item 36 judgement calls and the visual suite (this closes D-008)
- **Root causes of the visual failures at baseline (D-008).** Not one cause: (1) the Brief hook crashed on the list the test data returned for it, now it validates the shape and the test data returns a proper empty brief; (2) the case page crashed on cards added after the test data was written (review score, claim fields) that received a list where they expected an object, those cards now validate and the test data answers "not available" for those newer endpoints; (3) expectations that described screens redesigned before this build began. None of the failures hid a regression from this build, but (1) and (2) were real robustness gaps in the product and are fixed there, not in the tests.
- **Expectations changed on purpose** (recorded so nobody reads them as weakened): the chat landing moved from `/app` (now the Brief) to `/app/assistant` (gates 10, 11, 17, 18); the greeting is checked for morning, afternoon or evening (it was a test that only passed before noon, also the deployed-profile test); the composer placeholder, the not-configured wording ("Azure OpenAI. Configure ..."), the claim tab names without counts ("All -"), the case page's decision card (one primary action, the rest under More actions, Request missing documents only while a claim is in MissingDocuments), the snapshot id kept on the note as data-snapshot-id and not shown to people, the Knowledge hub (Upload and Re-index approved are workspace actions and are available; a source with unknown sensitivity still offers no lifecycle action), and the Policy page (a question is asked and the answer area is checked, instead of a pre-filled answer the page never had). Gate 1: a new person's sidebar opens expanded (240px) by design; the collapsed-rail checks set that choice first. No test was deleted or skipped.
- **A phone starts with the narrow rail.** With no saved choice and a viewport under 768px, the sidebar is the 64px rail. A saved choice always wins. Reason: with the 240px default a 390px phone left 150px for the page and hid content (found by the visual suite).
- **The rail opens on keyboard focus only.** Opening it on any focus made a tap or click re-flow the list under the finger, so the press ended on another row and the tap was lost. Hover still opens it for a mouse.
- **Muted text colour darkened from #6B7280 to #646C7A.** The design language quoted 4.83:1 against white but the page background is #F5F6F8, where it measured 4.47:1, below AA. The token and the document were both updated.
- **The shared Academy `ModuleView` keeps its CIP-style hex classes.** It is shared with the existing course player, and changing it would change a screen outside this item; the learner pages around it use the tokens.
- **Not done:** a pixel-diff visual baseline set was not added; the suite checks structure, accessibility and overflow, and screenshots are attached to each run for a person to look at.
